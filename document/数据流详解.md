# 数据流详解：从编码器到 RViz

## 一、节点流程图

```
┌──────────────────────────────────────────────────────────────────────┐
│                           物理层                                      │
│                                                                       │
│  STS3215 舵机 ×6                                                      │
│  每个舵机内部有一个磁编码器 (12bit, 0-4095)                             │
│  当前位置 = Present_Position 寄存器值 (0-4095)                         │
│                                                                       │
│  关节1 编码器: 2201    ← 这个值由标定时的物理位置决定                    │
│  关节2 编码器: 2265                                                   │
│  关节6 编码器: 1817  (闭合时≈1706, 全开时≈3158)                       │
└────────────────────┬─────────────────────────────────────────────────┘
                     │ 串口读取 (sync_read, 50Hz)
                     ▼
┌──────────────────────────────────────────────────────────────────────┐
│  motor_bridge (so101_hw_interface)                                    │
│                                                                       │
│  步骤1: 读编码器原始值                                                 │
│    raw[i] = bus.sync_read("Present_Position")  # 0-4095 整数          │
│                                                                       │
│  步骤2: 套公式转弧度                                                  │
│    position_rad[i] = (raw[i] - homing_offset[i]) × 2π ÷ 4096           │
│                        ↑                  ↑                           │
│                    编码器读数          标定文件的零位定义                │
│                                                                       │
│  步骤3: 发布                                                          │
│    → /so101_follower/joint_states (sensor_msgs/JointState)            │
└────────────────────┬─────────────────────────────────────────────────┘
                     │ /so101_follower/joint_states
                     ▼
┌──────────────────────────────────────────────────────────────────────┐
│  TopicBasedSystem (ros2_control 硬件插件)                              │
│                                                                       │
│  订阅 /so101_follower/joint_states → 填入 state_interfaces            │
│  读取 command_interfaces → 发布 /so101_follower/joint_commands        │
└────────┬───────────────────────────┬─────────────────────────────────┘
         │ state_interfaces          │ command_interfaces
         ▼                           ▼
┌────────────────────┐   ┌──────────────────────────────────┐
│ joint_state_       │   │ arm_controller                   │
│ broadcaster        │   │ gripper_controller               │
│                    │   │ (joint_trajectory_controller)     │
│ 读: state_ifaces   │   │                                  │
│ 发: /joint_states  │   │ 收: action goal                  │
└────────┬───────────┘   │ 写: /so101_follower/joint_commands│
         │               └──────────────────────────────────┘
         │ /joint_states
         ▼
┌──────────────────────────────────────────────────────────────────────┐
│  robot_state_publisher                                                │
│                                                                       │
│  输入: /joint_states (关节角度) + URDF (连杆结构)                      │
│  输出: /tf (每个 link 的 3D 位姿变换)                                  │
│                                                                       │
│  对每个关节:                                                          │
│    T_child = T_parent × origin_rpy × rotate(axis, joint_angle)        │
│                        ↑               ↑             ↑                │
│                     URDF写死的       URDF写死的    /joint_states的值    │
└────────────────────┬─────────────────────────────────────────────────┘
                     │ /tf
                     ▼
┌──────────────────────────────────────────────────────────────────────┐
│  RViz (MoveIt2)                                                       │
│                                                                       │
│  订阅 /tf → 渲染每个 link 的位置和姿态                                 │
│  订阅 /joint_states → 显示关节角度数值                                 │
│  加载 URDF → 知道每个 link 长什么样                                    │
└──────────────────────────────────────────────────────────────────────┘
```

## 二、启动时每个关节的角度由谁决定

motor_bridge 启动时：

```
1. 读编码器:      raw[4] = 2595        ← 硬件当前值，由物理位置决定

2. 套公式:        angle = (2595 - 2595) × 2π ÷ 4096 = 0°
                      ↑         ↑
                   编码器    homing_offset (标定文件)

3. 发布:          /joint_states: joint 4 = 0°
```

**homing_offset 不是目标位置**，它是"翻译规则"。同一个编码值 2595：
- 如果 homing=2595：角度 = 0°
- 如果 homing=2495：角度 = +8.8°
- 如果 homing=2695：角度 = -8.8°

物理臂完全没动，但 RViz 里显示的角度变了。因为你改了翻译规则。

## 三、RViz 展示的状态从哪里来

```
数据源:
  /joint_states    → 关节角度数值（6个浮点数）
  URDF             → 每个连杆的 3D 模型 + 关节安装位置/方向

渲染过程 (robot_state_publisher):
  以关节4为例:
    URDF 定义: 关节4在 parent link 上位于 (x,y,z)，旋转轴是 (0,1,0)
    当前角度:  从 /joint_states 读到 0°
    → 绕 Y 轴转 0° → 得到子 link 的位姿 → 发布 /tf

  RViz:
    收到 /tf → 把 URDF 里的 3D 模型放到对应位姿 → 渲染
```

## 四、标定文件 vs URDF 的"零位约定"

```
标定: homing_offset = 编码器读数值 → 关节角 = 0
URDF: joint angle = 0 → CAD 模型某个固定姿态（设计师定义）
```

**两边零位一致 = 对齐。不一致 = RViz 姿势 ≠ 真机姿势。**

URDF 里 6 个关节的 limits 定义了零位的"位置"：

| 关节 | lower | upper | 0 在什么位置 | 标定规则匹配？ |
|------|-------|-------|-------------|---------------|
| 1 | -1.92 | 1.92 | 中间 | ✓ |
| 2 | -1.75 | 1.75 | 中间 | ✓ |
| 3 | -1.75 | 1.57 | 中间 | ✓ |
| 4 | -1.66 | 1.66 | 中间 | ✓ |
| 5 | -2.79 | 2.79 | 中间 | ✓ |
| 6 | -0.17 | 1.75 | **贴着下限(≈闭合)** | ✗ |

## 五、为什么改装夹爪的 homing_offset

```
标定脚本给关节6:     homing = (1706+3158)/2 = 2432  → 半开=0° → RViz闭合 ✗
我们改到:           homing = 1817                    → 闭合=-0.17 → RViz闭合 ✓
```

## 六、实战问题 & 解决方案

### 问题1：RViz 和真机初始姿势完全不同（Z形 vs S形）

**现象**：motor_bridge 启动后自动把所有关节拉到中值位置，导致真机突然抖动到 S 形，而 RViz 显示的是 URDF 零位（竖直）。

**根因**：`motor_bridge.py` 的 `_initial_move_done` 逻辑在首次读编码器后，把每个关节命令到中值 `(range_min+range_max)/2`。

**解法**：注释掉 `_initial_move_done` 块，换为 `self._initial_move_done = True`。启动后机械臂保持当前位置不动，由用户自行控制。

---

### 问题2：标定文件路径不对，改了白改

**现象**：运行 `so101_calibrate` 后标定结果写入 `~/.so101_follower_calibration.yaml`，但 motor_bridge 读的是包里的 `config/so101_calibration.yaml`。每次都显示旧标定。

**根因**：标定脚本的写入路径和 motor_bridge 的读取路径不一致。

**解法**：每次标定后手动覆盖：
```bash
cp ~/.so101_follower_calibration.yaml \
   <repo>/src/so101_hw_interface/config/so101_calibration.yaml
```

---

### 问题3：关节4、5 零位偏差 90°

**现象**：关节4（wrist_flex）、关节5（wrist_roll）在 RViz 里显示 0° 时，真机实际弯了/转了约 90°。

**根因**：标定文件里的 `homing_offset` 是另一台机器的值。虽然 encoder 读数只差几到几十步，但 URDF 里关节 4、5 的 origin rpy 经过复杂空间旋转后，几度的零位偏差在视觉上被放大。

同时 `range_min/range_max` 也是别人的物理极限值，导致标定脚本算的 "中值" 对不上你的机器。

**解法**：重新运行 `so101_calibrate`，对每个关节手动扳到物理极限并回到零位。这样 `range_min/range_max/homing_offset` 三个值都是你这台机器的真实值。

---

### 问题4：夹爪不对齐（闭合 vs 半开）

**现象**：标定后关节4、5、1/2/3 都对齐了，但夹爪（关节6）的 homing_offset = 2432 是中值，导致真机半开时 RViz 显示闭合。

**根因**：标定脚本对所有 6 个关节用同一个规则 `homing = (min+max)/2`（中值=0°）。关节 1-5 的 URDF limits 对称（±1.9），0 在中间，匹配。但关节 6 的 URDF limits 不对称：`lower=-0.17 upper=1.75`，0 贴着下限（闭合≠中值）。

**解法**：手动把关节6的 `homing_offset` 改为 `range_min + 111`，使 "物理闭合 = -0.17 rad"，对齐 URDF 的 lower limit。
```
homing = range_min + (0 - lower_urdf) × 4096/(2π)
       = range_min + 0.17 × 652
       = range_min + 111
```

---

### 问题5：关节5 方向反了

**现象**：关节5 转动方向正确、幅度正确，但 RViz 里夹爪向上开、真机向下开。

**根因**：电机的物理旋转正方向与 URDF 定义的关节轴正方向相反。这不是标定能解决的——`homing_offset` 只管零位，方向由电机硬件/URDF axis 定义。

**解法**：重新标定，标定时用手扳关节注意**往 RViz 正向的方向移动**。如果方向仍不对，在标定文件中给该关节加 `direction: -1` 字段，由 motor_bridge 自动取反。

---

### 总结：对齐检查清单

| 步骤 | 做什么 | 怎么验证 |
|------|--------|---------|
| 1 | `so101_calibrate` 标定 | 覆盖 `config/so101_calibration.yaml` |
| 2 | 启动 motor_bridge | 不发命令，看 RViz 是否重现真机姿势 |
| 3 | 测试关节1-5 正反30° | `ros2 action send_goal` 看方向和幅度 |
| 4 | 关节6 homing_offset = range_min + 111 | 闭合时 RViz 也闭合 |
| 5 | 关节5 如果方向反 | 重标定 或 加 `direction: -1` |
